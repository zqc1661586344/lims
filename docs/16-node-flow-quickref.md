# LIMS 全流程 16 节点速查表

> 用途：从**任务委托提交**到**项目归档**完整走完一个委托的操作速查。
> 核心规则：**每个节点 = 到该节点页面「新增(委托ID=流程实例ID)」→ 保存 → 在该记录上「通过」→ 流程推进到下一节点。**

## 一、16 节点流转顺序（速查）

```
任务创建 → 合同评审 → 质控任务 → 采样调度 → 现场采样 → 样品接收
→ 任务分配 → 数据录入 → 数据复核 → 数据审核 → 报告编制 → 报告复核
→ 报告审核 → 报告签发 → 报告发放 → 项目归档 ✅
```

| 步 | 节点 | 责任部门 | 你在这个页面做什么 | 可驳回到 |
|----|------|---------|------------------|---------|
| 1 | 任务创建 | 业务室 | **任务创建**页新增委托 + 提交（提交即启动流程） | — 流程起点，不可驳回 |
| 2 | 合同评审 | 技术室 | 合同评审页新增 + 通过 | ① 任务创建 |
| 3 | 质控任务 | 质控室 | 质控任务页新增 + 通过 | ② 合同评审 |
| 4 | 采样调度 | 现场室 | 采样调度页新增 + 通过 | ③ 质控任务 |
| 5 | 现场采样 | 现场室 | 现场采样页新增 + 通过 | ④ 采样调度 |
| 6 | 样品接收 | 样品室 | 样品接收页新增 + 通过 | ⑤ 现场采样 |
| 7 | 任务分配 | 实验室 | 任务分配页新增 + 通过 | ⑥ 样品接收 |
| 8 | 数据录入 | 实验室 | 数据录入页新增 + 通过 | ⑦ 任务分配 |
| 9 | 数据复核 | 实验室 | 数据复核页新增 + 通过 | ⑧ 数据录入 |
| 10 | 数据审核 | 实验室 | 数据审核页新增 + 通过 | ⑨ 数据复核 |
| 11 | 报告编制 | 报告室 | 报告编制页新增 + 通过（填报告编号/编制意见） | ⑩ 数据审核 |
| 12 | 报告复核 | 实验室 | 报告复核页新增 + 通过 | ⑪ 报告编制 |

| 16 | 项目归档 | 报告室 | 项目归档页新增 + 通过（归档完成，流程结束） | — 终节点，不可驳回 |

## 二、每个节点的标准操作（重复这套即可）

对除第 1 步外的节点 2~16：

```
① 到对应节点的业务页面 → 点「新增/新建」
② 填写业务数据（关键：委托ID 填「流程实例 id」，即王小二=8 那个数字）
③ 保存 → 列表出现这条记录
④ 在这条记录上点「通过」→ 弹「…通过，流程已推进」
⑤ 到「待办任务」页确认当前节点已变为下一节点
→ 循环到下一节点
```

> 最后一个节点「项目归档」点「通过」后，流程 `status` 会变为 `completed`，整个委托走完。

## 三、关键原则（务必记住）

1. **委托ID = 流程实例ID**：你建的那条委托在 `task_orders` 表的 `id`（如王小二=8）。所有业务节点页的「委托ID」都要填这个数字，填错(如 985)会导致「未找到该委托当前待办的任务」。
2. **先增后批**：每个节点必须先**在该节点页面录入业务数据**，再点**通过**。只去「待办任务」页点通过、而不在业务页面录入数据，会导致该节点没有业务记录（页面空白是正常的）。
3. **审批只推进指针**：「待办任务」页的「处理→通过」只把流程指针移到下一节点，**不会自动生成**业务记录。
4. **业务记录 id ≠ 流程任务 id**：页面里的记录 id 是业务表主键；流程推进用的是 `process_tasks` 里的任务 id（后端已自动按委托ID解析，前端无需关心）。

## 四、验证流程是否正确推进（可选，用命令）

```bash
# 查看所有流程实例当前停在哪一步
docker exec -it $(docker ps -qf name=postgres) psql -U lims -d lims -c \
  "SELECT id, current_node, status FROM process_instances ORDER BY id DESC;"
```

- `current_node` = 当前停留节点（如 `node_data_entry`）
- `status` = `running`（进行中）或 `completed`（已归档完成）

对应关系：`node_task_create`任务创建 / `node_contract_review`合同评审 / `node_qc_task`质控任务 / `node_sampling_schedule`采样调度 / `node_field_sampling`现场采样 / `node_sample_receiving`样品接收 / `node_task_assign`任务分配 / `node_data_entry`数据录入 / `node_data_review`数据复核 / `node_data_audit`数据审核 / `node_report_prepare`报告编制 / `node_report_review`报告复核 / `node_report_audit`报告审核 / `node_report_sign`报告签发 / `node_report_print`报告发放 / `node_project_archive`项目归档。

## 五、SoD 职责分离约束

为符合 CNAS 实验室资质要求，系统内置 **7 条职责分离（Segregation of Duties）** 规则：**同一用户不能在相邻的两个关键节点都参与操作**。非 admin 用户在"通过/驳回"时系统会自动校验，违反会返回 `职责分离校验失败` 错误。

| 当前节点 | 冲突前置节点（这些节点的操作人不能是你） | 业务含义 |
|---------|--------------------------------------|---------|
| ② 合同评审 | ① 任务创建 | 业务经理不能自己创建委托再自己评审合同 |
| ⑥ 样品接收 | ⑤ 现场采样 | 采样员不能自己采样再自己接收样品 |
| ⑨ 数据复核 | ⑧ 数据录入 | 录入员不能自己录入再自己复核 |
| ⑩ 数据审核 | ⑧ 数据录入、⑨ 数据复核 | 审核人不能是录入人或复核人 |
| ⑫ 报告复核 | ⑪ 报告编制 | 报告编制人不能自己复核自己的报告 |
| ⑬ 报告审核 | ⑪ 报告编制、⑫ 报告复核 | 审核人不能是编制人或复核人 |
| ⑭ 报告签发 | ⑪ 报告编制 | 报告编制人不能自己签发自己的报告 |

> **admin 用户不受 SoD 约束**：管理员账号可在任意节点审批、不受职责分离限制（但建议仅用于测试和异常恢复）。

## 六、驳回规则

流程支持**向前一步驳回**，被驳回的节点数据会被清空，当前节点指针回到上一步。

- **驳回 1 步**：`current_node = current_node - 1`（线性回退）
- **流程起点（① 任务创建）不可驳回**：`definition.go` 定义了 `CanReject: false`
- **终节点（⑯ 项目归档）不可驳回**：`CanReject: false`
- 驳回后上一步的**责任部门和操作人会重新变成"待处理"**，对应部门用户会在「我的待办」看到这条任务

> 第一节的「可驳回到」列已列出每个节点的驳回目标，可直接查表。

## 七、admin 用户的特殊权限

admin 用户（`users.is_admin = true`）拥有以下 3 项豁免，普通用户没有：

| 特权 | 实际效果 |
|------|---------|
| **绕过部门校验** | 任意部门的待办任务都能处理（不受 `assignee_dept_id` 限制） |
| **绕过 SoD 校验** | 审批/驳回时不检查职责分离 |
| **绕过数据范围** | 查看所有部门的业务数据（`ApplyTaskOrderScope` 直接返回原查询） |

> **场景**：
> - 测试：用 admin 跑通整条 16 节点流程，不受 SoD 限制
> - 异常恢复：某用户请假或 SoD 冲突时，admin 代审批推进流程
> - 审计：admin 可查询全部门数据、Workflow 实例历史

> **注意**：admin 仅绕过代码层面的约束，但业务合规责任仍需人工把控。生产环境建议只将 admin 角色分配给系统管理员 1~2 人。
