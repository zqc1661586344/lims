# 检测管理流转说明

> 本文档基于 `docs/process.md` 业务流程图与 `backend/internal/workflow/definition.go` 状态机整理，描述完整"检测管理"从开始到结束的执行顺序。

## 一、流程总览

流程从**任务创建**开始，最终到**项目归档**结束。共 **16 个节点**，每一步必须等当前节点"通过"（审核）才触发下一步。每个节点对应一个责任部门，并在相应步骤产出流程文档（D1–D15）。

```
业务室 → 技术室 → 质控室 → 现场室 → 现场室 → 样品室
     实验室 → 实验室 → 实验室 → 实验室
                   报告室 → 实验室 → 质控室 → 技术室
                   业务室 → 报告室（归档结束）
```

## 二、16 个节点逐步流转顺序

| 步骤 | 节点 | 责任部门 | 环节内容 / 产出文档 |
|---|---|---|---|
| 1 | 任务创建 | 业务室 | 录入客户、项目、样品、检测项目，生成**委托任务单（D1）**，启动流程 |
| 2 | 合同评审 | 技术室 | 评审合同/协议，产出**检测合同/协议（D2）** |
| 3 | 质控任务 | 质控室 | 在检测任务中加质控方案，产出**委托检测方案（D3）** |
| 4 | 采样调度 | 现场室 | 安排采样团队、点位、设备 |
| 5 | 现场采样 | 现场室 | 现场采样，产出**现场采样记录及设备校准记录（D4）** |
| 6 | 样品接收 | 样品室 | 接收样品、编码登记，产出**样品接收记录（D5）** |
| 7 | 任务分配 | 实验室 | 把检测项目分配给实验员 |
| 8 | 数据录入 | 实验室 | 录入检测数据，产出**实验原始记录（D6）** |
| 9 | 数据复核 | 实验室 | 复核数据，**实验原始记录（D7）** |
| 10 | 数据审核 | 实验室 | 审核数据，**实验原始记录（D8）** |
| 11 | 报告编制 | 报告室 | 编制报告，产出**报告 + 实验原始记录（D9）** |
| 12 | 报告复核 | 实验室 | 复核报告，**报告 + 实验原始记录（D10）** |
| 13 | 报告审核 | 质控室 | 审核报告，**报告 + 实验原始记录（D11）** |
| 14 | 报告签发 | 技术室 | 签发盖章，产出**最终版报告 + 原始记录（D12）** + **报告审核签发单（D15，汇聚 D9–D11）** |
| 15 | 报告发放 / 打印 | 业务室 | 打印发放给客户，产出**报告发放记录（D13）** |
| 16 | 项目归档 | 报告室 | 把 D1–D13 **所有文档**归档（D14），流程结束 |

## 三、部门泳道流转（简短版）

> 业务室(1) → 技术室(2) → **质控室(3)** → 现场室(4) → 现场室(5) → 样品室(6) → 实验室(7,8,9,10) → 报告室(11) → 实验室(12) → 质控室(13) → 技术室(14) → 业务室(15) → 报告室(16)

## 四、文档流转关系（D1–D15）

- **D1–D5**：委托任务单 → 检测合同 → 委托检测方案 → 现场采样记录及设备校准记录 → 样品接收记录
- **D6–D8**：实验原始记录（数据录入/复核/审核三环节）
- **D9–D11**：报告 + 实验原始记录（编制/复核/审核三版）
- **D12**：最终版报告 + 原始记录（报告签发后定稿）
- **D15**：报告审核签发单（汇聚 D9–D11，在签发环节产出）
- **D13**：报告发放记录
- **D14**：以上所有文档（汇聚 D1–D13，在项目归档环节落入归档清单）

```
D9 ──┐
D10 ─┼──► D15（报告审核签发单）──► D12（最终版报告，签发环节定稿）
D11 ─┘

D1 ──┐
D2 ──┤
... ─┼──► D14（以上所有文档）──► 项目归档
D13 ─┘
```

## 五、代码驱动机制

- 流程状态机定义于 `backend/internal/workflow/definition.go`，每个节点包含 `Code`（节点码）、`Name`（中文名）、`DeptCode`（责任部门）、`NextNode`（下一个节点）、`CanReject`（是否允许驳回）、`RejectTarget`（驳回到哪）。
- 节点"通过"时，`workflow.Engine.ApproveTaskWithTx` 自动创建下一节点待办；"驳回"时，`RejectTaskWithTx` 清空当前节点业务数据、回退流程指针。
- 审批/驳回前会依次执行三层校验（admin 用户全绕过）：
  1. **部门校验**：`task.assignee_dept_id = user.dept_id`，只有当前节点责任部门的用户能处理
  2. **SoD 校验**：非 admin 用户需通过 `checkSoD` 职责分离检查（见第六节）
  3. **指派校验**：`assignee_user_id != 0` 时，必须是指派的用户才能处理
- 待办展示于前端「待办任务」页，按当前节点责任部门的**部门待办** / **我的待办**筛选展示。

## 六、SoD 职责分离约束

为符合 CNAS 实验室资质要求，系统内置 **7 条职责分离（Segregation of Duties）** 规则——**同一用户不能在相邻的两个关键节点都参与操作**。非 admin 用户在"通过/驳回"时系统自动校验，违反会返回 `职责分离校验失败` 错误。

| 当前节点 | 冲突前置节点（这些节点的操作人不能是你） | 业务含义 |
|---------|--------------------------------------|---------|
| ② 合同评审 | ① 任务创建 | 业务经理不能自己创建委托再自己评审合同 |
| ⑥ 样品接收 | ⑤ 现场采样 | 采样员不能自己采样再自己接收样品 |
| ⑨ 数据复核 | ⑧ 数据录入 | 录入员不能自己录入再自己复核 |
| ⑩ 数据审核 | ⑧ 数据录入、⑨ 数据复核 | 审核人不能是录入人或复核人 |
| ⑫ 报告复核 | ⑪ 报告编制 | 报告编制人不能自己复核自己的报告 |
| ⑬ 报告审核 | ⑪ 报告编制、⑫ 报告复核 | 审核人不能是编制人或复核人 |
| ⑭ 报告签发 | ⑪ 报告编制 | 报告编制人不能自己签发自己的报告 |

> **admin 用户不受 SoD 约束**：管理员账号可在任意节点审批、不受职责分离限制。

## 七、驳回规则

流程支持**向前一步驳回**，被驳回的节点业务数据会被清空，流程指针回到上一步。

- **驳回目标由 `RejectTarget` 硬编码**（definition.go 每个节点都明确定义），目前是线性回退：节点 2→1，节点 3→2，…，节点 15→14
- **流程起点（① 任务创建）不可驳回**：`CanReject: false`
- **终节点（⑯ 项目归档）不可驳回**：`CanReject: false`
- 驳回后上一步的责任部门和操作人会重新变为"待处理"，对应部门用户会在「待办任务」看到这条任务

> 速查表第一节的「可驳回到」列可直接查阅每个节点的驳回目标。

## 八、admin 用户的特殊权限

admin 用户（`users.is_admin = true`）拥有以下 3 项豁免，普通用户没有：

| 特权 | 实际效果 |
|------|---------|
| **绕过部门校验** | 任意部门的待办任务都能处理（不受 `assignee_dept_id` 限制） |
| **绕过 SoD 校验** | 审批/驳回时不检查职责分离 |
| **绕过数据范围** | 查看所有部门的业务数据（`ApplyTaskOrderScope` 直接返回原查询） |

> 使用场景：
> - **测试**：用 admin 跑通整条 16 节点流程，不受 SoD 限制
> - **异常恢复**：某用户请假或 SoD 冲突时，admin 代审批推进流程
> - **审计**：admin 可查询全部门数据、Workflow 实例历史

> 生产环境建议只将 admin 角色分配给系统管理员 1~2 人，避免滥用。

## 九、一句话总结

> **第 1 步任务创建（业务室）开始 → 依次经过合同评审（技术室）→ 质控（质控室）→ 采样（现场室）→ 样品接收（样品室）→ 数据三环节（实验室）→ 报告编制（报告室）→ 报告复核/审核/签发（实验室→质控室→技术室）→ 报告发放（业务室）→ 项目归档（报告室）结束。**
